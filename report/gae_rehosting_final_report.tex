\begin{abstract}
GAMA Animation Engine (GAE), a component of the Gamatutor project, is a native Windows desktop application for creating and playing tutorial animations. Although the application remains useful, its Windows-native form limits accessibility because users normally need a compatible Windows device and a local installation. This project addresses that limitation through cloud rehosting. The implemented system runs GAE on a Windows EC2 instance and provides browser-based access through Apache Guacamole deployed on a Linux EC2 instance. Users interact with GAE from a web browser, while Guacamole forwards the session to the Windows server using Remote Desktop Protocol (RDP). The result shows that GAE can be accessed across operating systems without installing the application on each local device and without significantly modifying the original application. The project demonstrates that rehosting is a practical approach when the main requirement is cross-platform, browser-only access rather than a full cloud-native redesign.
\end{abstract}

\begin{IEEEkeywords}
cloud computing, rehosting, legacy application, Apache Guacamole, AWS EC2, Remote Desktop Protocol, cross-platform access, GAMA Animation Engine
\end{IEEEkeywords}

\section{Introduction}

Many applications that remain useful in academic or institutional settings were not designed for today's multi-device environment. Some were built as native desktop applications and are therefore tied to a particular operating system. GAMA Animation Engine (GAE), part of the Gamatutor project, is one such case. The application provides desktop tools such as TutorialGenerator and PlayerAnimasi for creating and running tutorial animation content.

The main issue addressed in this project is accessibility. In its original deployment model, GAE is most practical when the user has a compatible Windows environment and can prepare the application locally. This creates friction for users on macOS, Linux, Chromebook, or other devices that cannot run Windows desktop applications directly. It also makes distribution less efficient because the same setup process must be repeated on multiple user devices.

To address this issue, the project keeps GAE as a Windows desktop application but moves its execution environment to the cloud. The user no longer needs to install the application locally. Instead, the user opens a browser and accesses a remote Windows session where GAE is already installed. The design is therefore built around four goals: cross-platform access, browser-only usage, minimal local setup, and preservation of the original application behavior.

The final implementation uses Apache Guacamole as a browser-based remote desktop gateway and Amazon Elastic Compute Cloud (EC2) as the infrastructure platform. A Linux EC2 instance hosts the Guacamole gateway, while a Windows EC2 instance runs GAE. This report presents the design, implementation, testing result, limitations, and required appendices for the final cloud computing project deliverable.

\section{Methods}

\subsection{Application and Problem Analysis}

GAE was analyzed as a Windows-native desktop application. Based on the project proposal and application characteristics, GAE is built using Delphi/Object Pascal with the Visual Component Library (VCL), runs as a standalone Windows application, and uses local assets such as animation files, images, and audio. These characteristics make the application dependent on a Windows desktop environment.

The access problem is straightforward: users need the correct operating system and local setup before they can use the application. For a classroom or shared-use scenario, this is inconvenient because every user device must be prepared separately. The project therefore requires a deployment model that keeps the Windows runtime available while presenting the application through an interface that is common across devices. A web browser was selected as that interface.

\subsection{Migration Strategy}

The selected strategy is rehosting, often called lift-and-shift. Rehosting moves the application execution environment to cloud infrastructure with minimal changes to the application itself. This strategy is appropriate because the project is not trying to rebuild GAE as a web application. The intended outcome is to make the existing application easier to access.

Other approaches were considered less suitable for this project scope. A complete web rewrite would require redesigning the user interface, runtime model, and file handling behavior. A cloud-native redesign would also require a larger engineering effort and could change how the application behaves. Rehosting is more realistic because it preserves the Windows desktop environment while improving access through a cloud-based gateway.

\subsection{Target Architecture}

The architecture has three layers: client, gateway, and application host. The client layer is the user's device and web browser. The gateway layer is a Linux EC2 instance running Apache Guacamole and its supporting services. The application host is a Windows EC2 instance where GAE is installed and executed.

\subsection{Deployment Procedure}

The implementation was carried out in two stages. The first stage was a local proof of concept using a virtualized Windows environment. The second stage moved the architecture to AWS.

The cloud deployment procedure was as follows:

\begin{enumerate}
    \item Configure AWS budget monitoring to reduce the risk of unexpected cost.
    \item Create the required network components, including VPC, subnet, route table, and internet gateway.
    \item Launch a Linux EC2 instance for Apache Guacamole.
    \item Launch a Windows EC2 instance for the GAE application.
    \item Configure security groups so that users access Guacamole through the browser, while RDP access to Windows is restricted to the internal network or the Guacamole gateway.
    \item Install Docker and Docker Compose on the Linux EC2 instance.
    \item Deploy Guacamole, \texttt{guacd}, and database services using the deployment repository.
    \item Install or copy the GAE application artifact to the Windows EC2 instance.
    \item Create an RDP connection entry in Guacamole that points to the Windows EC2 instance.
    \item Test access from a browser and compare it with the local proof-of-concept environment.
\end{enumerate}

\subsection{Repositories}

Two repositories were used. The original GAE/Gamatutor repository provides the application artifact and source materials for the application being rehosted \cite{gamatutor}. The project deployment repository contains Docker-based configuration for the Guacamole gateway layer \cite{deployment-repo}. This distinction is important because the project does not claim to rebuild GAE. The contribution of this project is the cloud rehosting environment that makes the existing application accessible through a browser.

\section{Results}

\subsection{Local Proof of Concept}

The first milestone was a local proof of concept using VirtualBox. The team installed GAE inside a local Windows virtual machine and verified that the environment could be accessed through RDP. At that stage, Guacamole integration was not yet complete, and the reported progress was 40\%. This result confirmed that the application could run in a virtualized Windows environment and could be reached remotely.

\subsection{Cloud Rehosting Result}

The final deployment successfully rehosted GAE using the architecture in Fig.~\ref{fig:architecture}. Users access Guacamole from a browser. Guacamole then opens an RDP session to the Windows EC2 instance where GAE is installed. The team reported the final implementation as 100\% complete after the browser-based access flow was verified.

The result satisfies the main accessibility goals. Users do not need to install GAE on their local devices. Users on different operating systems can access the same application environment through a browser. The Windows-specific runtime is centralized in the cloud, while the browser becomes the main user-facing interface.

\subsection{Functional Testing}

\subsection{Deployment Configuration Result}

The deployment repository uses Docker Compose to define the Guacamole gateway environment. The main services are Guacamole, \texttt{guacd}, and a MariaDB/MySQL database. During the prototype stage, Guacamole was exposed through port 8080. The \texttt{guacd} service handled the protocol translation to RDP, while the database stored user and connection configuration.

Docker Compose made the gateway setup more repeatable because the required services could be started together on the Linux EC2 instance. The prototype configuration also highlighted several security points that need improvement, especially the treatment of access values and configuration files.

\section{Discussion}

\subsection{Accessibility Improvement}

The strongest contribution of the project is not a new application feature, but a more accessible delivery model. In the original model, the user must prepare a Windows environment. In the rehosted model, the user only needs a browser. This changes the user requirement from installing a Windows desktop application into opening a browser and connecting to a hosted session.

This is useful for cross-platform scenarios. A user on Windows, macOS, Linux, or another browser-capable device can access the same GAE environment. It also simplifies maintenance because the application can be prepared once on the Windows EC2 instance rather than repeatedly installed on many local machines.

\subsection{Why Rehosting is Suitable}

Rehosting fits the project scope because the goal is accessibility, not application redevelopment. Keeping GAE inside a Windows environment preserves the original behavior. Placing Guacamole in front of that environment makes the application reachable from a browser. The combination directly solves the project problem with a manageable amount of infrastructure work.

A full cloud-native redesign would require a different project scope. It would involve rewriting the interface for the web, redesigning local file handling, and building a new application architecture. Those changes may be valuable in the future, but they are not necessary to validate browser-based access for the current project.

\subsection{Security Considerations}

Remote desktop access must be configured carefully. The Windows EC2 instance should not expose RDP directly to the public internet. RDP should be limited to the Guacamole gateway or private network rules. The Guacamole interface should also use HTTPS in a production environment, and administrative access should be limited to trusted users.

The prototype configuration still contains classroom-level shortcuts. These should be improved before any production use. A stronger deployment should use separated environment configuration, restricted network rules, and non-default Guacamole accounts.

\subsection{Operational Limitations}

The solution remains dependent on a Windows EC2 instance. This means it has the operational characteristics of a remote desktop environment rather than a lightweight web application. Cost, instance uptime, Windows licensing, session stability, and network quality all affect the user experience.

The project also focuses on feasibility instead of detailed performance evaluation. No formal latency benchmark, bandwidth benchmark, or concurrent-user stress test was performed. Future work should include those measurements, especially if the system will be used by multiple users at the same time.

\subsection{Future Improvements}

Several improvements can make the system more production-ready. HTTPS should be configured using a domain and TLS certificate. Authentication should use unique accounts and stronger access policies. RDP access should be restricted using private networking and security group references. Backup should be prepared for animation files and Guacamole configuration. Cost can also be reduced by stopping instances when they are not used or by scheduling runtime based on class activity.

\section{Conclusion}

This project successfully improved access to GAE by rehosting the Windows-native application in a cloud environment. The implementation uses a Linux EC2 instance running Apache Guacamole as the browser-based gateway and a Windows EC2 instance as the application host. With this architecture, users can access GAE from different operating systems without installing the application locally.

The result shows that rehosting is a practical strategy when the main objective is to make an existing desktop application easier to reach. The system does not convert GAE into a cloud-native application, but it achieves the intended outcome: cross-platform, browser-based, no-install access while preserving the original Windows application behavior.

\section{Step-by-Step Documentation}

This appendix describes the rehosting procedure used in the project. Deployment-specific values such as instance identifiers and IP addresses should be adjusted according to the active environment.

\subsection{Prepare AWS Budget and Network}

Create an AWS budget to monitor usage cost. Then create a VPC for the project. The VPC should contain a subnet for the Guacamole gateway and routing through an internet gateway. The Windows instance should be reachable from the Guacamole gateway but should not expose RDP directly to the public internet.

\subsection{Launch Linux EC2 for Guacamole}

Launch an Ubuntu Linux EC2 instance. Attach a security group that allows administrative SSH access from a trusted network and allows browser access to the Guacamole prototype port. In production, port 8080 should be placed behind HTTPS using a reverse proxy.

\subsection{Install Docker and Docker Compose}

Install Docker and Docker Compose on the Linux EC2 instance. The exact command sequence may vary depending on the operating system image, but the goal is to prepare the instance so it can run the Guacamole Docker Compose stack.

\subsection{Deploy Guacamole Services}

Clone the deployment repository and start the Docker Compose services. The repository contains the configuration for Guacamole, \texttt{guacd}, database, and supporting folders.

\begin{lstlisting}[style=code]
git clone https://github.com/EarlyOcean/cloud-computing-final-project.git
cd cloud-computing-final-project
mkdir -p init data drive record
docker compose up -d
\end{lstlisting}

After the containers are running, verify the service status using Docker Compose. Then open the Guacamole interface from a browser using the Linux EC2 public address and the configured web port.

\subsection{Launch Windows EC2 for GAE}

Launch a Windows Server EC2 instance. Configure its security group so that RDP port 3389 is reachable only from the Guacamole gateway or the internal VPC.

\subsection{Install GAE on Windows EC2}

Download the original Gamatutor/GAE application artifact from the official repository. Install or copy the required files to the Windows EC2 instance. Verify that TutorialGenerator and PlayerAnimasi can be executed in the Windows environment.

\begin{lstlisting}[style=code]
https://github.com/gamatutor/gamatutor
\end{lstlisting}

\subsection{Create Guacamole RDP Connection}

Log in to Guacamole as an administrator and create a new RDP connection. Configure the connection to point to the Windows EC2 instance. After saving the connection, open it from the Guacamole dashboard and verify that the Windows desktop appears in the browser.

\subsection{Run GAE Through Browser}

From the Guacamole session, run the GAE application on the Windows EC2 desktop. The user should be able to interact with GAE without installing it locally. This verifies the main project goal: cross-platform browser-based access to a native Windows desktop application.
